# Studio conventions

This repo is a small animation and game studio. An agent authors scenes as code, renders them headless, and publishes a showcase to GitHub Pages. The owner directs and reviews.

## Toolchain

- Blender 4.5 LTS: `studio doctor --deep` prints the path.
- Godot 4.7.2 standard: same.
- Unity 6.3 LTS, GDevelop 5.6, LÖVE 11.5, .NET 10 and MonoGame: same.
- FFmpeg 9 with ffprobe.
- Python venv at `.venv` with Pillow, PyYAML, pytest.
- Node 24+ with pnpm 11 for `showcase/`.

Never commit `.venv`, `node_modules`, raw frames, Godot `.godot/`, or build output.

## Commands

```bash
./.venv/Scripts/python studio/studio.py doctor --deep
./.venv/Scripts/python studio/studio.py validate
./.venv/Scripts/python studio/studio.py new 2d 004-my-study --title "My Study"
./.venv/Scripts/python studio/studio.py render 001-2d-bounce
./.venv/Scripts/python studio/studio.py render 010-maker-at-work --preview
./.venv/Scripts/python studio/studio.py render 010-maker-at-work --shot s02-portrait
./.venv/Scripts/python studio/studio.py build 003-micro-game
./.venv/Scripts/python studio/studio.py build 011-bin-city --target windows
./.venv/Scripts/python studio/studio.py build 011-bin-city --target all
./.venv/Scripts/python studio/studio.py export 004-lantern-keeper
./.venv/Scripts/python studio/studio.py verify 004-lantern-keeper
./.venv/Scripts/python studio/studio.py assets verify --offline
./.venv/Scripts/python studio/studio.py teaser
./.venv/Scripts/python studio/studio.py publish
./.venv/Scripts/python -m pytest studio/tests -v
cd showcase && pnpm typecheck && pnpm build
```

## Engines

Every engine lives behind an adapter in `studio/lib/engines/`. `studio doctor --deep` reports version, path, supported kinds and blockers. A missing engine is a blocker, not a crash.

Manifests use `kind: film | game` and may declare `shots`. A shot has an id, an entry and a frame count. Shot frames must total `render.frames`. Projects without shots get one implicit `main` shot. Engine choice is independent of the showcase label.

## Assets

Three lanes: `repo/` committed and credited, `embed/` baked and not committed, `private/` owner files and not committed. Every asset has a catalog entry with license, source, path and sha256. Run `studio assets verify --offline` before committing. Mixamo is banned.

## Project anatomy

```
projects/<id>/
├─ project.yaml      manifest, the single source of truth
├─ render.py         Pillow renderer (type 2d)
├─ scene.py          Blender scene (type 3d)
├─ project.godot     Godot project (type game)
└─ README.md         what it is and how to reproduce it
```

Starter templates live in `studio/templates/{2d,3d,game,game3d}`. They use `__ID__` and `__TITLE__` placeholders that `studio new` substitutes. `studio/tests/test_templates.py` keeps them valid.

Manifest rules: id is `NNN-lowercase-name`, type is `2d | 3d | game`, kind is `film | game`, and the engine must be one the registry supports for that kind. Resolution never exceeds 1920x1080. Outputs are repo-relative paths. Blender exports go to the declared `.glb` output. Optional `render.poster_time` (seconds, default 1) picks the poster frame.

## Media rules

- GIF under 8 MB, MP4/WebM under 20 MB, card teaser under 2 MB, poster under 500 KB, GLB under 5 MB.
- `studio render` validates with ffprobe and refuses oversized output.
- Keep only curated output in `media/`. Raw frames live in `media/<id>/_frames/` and are ignored.
- A project needs `media/<id>/poster.jpg` before `studio publish` will include it.
- Long reels go to GitHub Releases, never git.

## Showcase data

`showcase/src/projects.generated.ts`, `showcase/public/media/`, `showcase/public/models/` and `showcase/public/builds/` are generated by `studio publish` and ignored by git. CI runs publish before every typecheck and build.

Game builds live under `builds/<id>/` so the `/play/<id>` route can fall back to the SPA shell instead of serving the game directory directly. A tracked web build is capped at 40 MB; anything larger ships as video plus a release download.

The site uses a `/animation-and-game-studio/` base path and ships route shells, `404.html` and `.nojekyll` so deep links resolve on Pages without a 404 status.

## Visual rules

- Light mode, warm cream backgrounds, ink text, one accent per scene.
- Restrained layout, but the landing hero should be distinctive.
- No em dashes in any copy.
- Respect `prefers-reduced-motion` on the site.

## Definition of done

1. Tests and `studio validate` pass.
2. Video output passes ffprobe checks at the declared resolution, fps and duration.
3. A still frame has been viewed and reads clearly.
4. `studio publish` has run and the site builds.
5. The deployed page has been opened in a real browser at desktop and mobile widths.
6. Commit in small conventional commits and push.

## AgentOS Constitution v2 - Hands-Off Autonomous Engineering

These laws apply to every agent (Hermes, Claude Code, Qoder, Antigravity) in every repository and folder. Repository-specific instructions may add detail but never weaken these laws.

### Law 1 - Full autonomy (zero hand-holding)
- You are an autonomous engineer. Do NOT ask the human for permission, confirmation, or clarification.
- The single exception: an action that would permanently destroy irrecoverable production data (dropping production databases, deleting the only copy of data, force-pushing over unreplicated history). Stop and ask only then.

### Law 2 - Anti-vibecoding and anti-slop
- NEVER use em-dashes (U+2014) or en-dashes (U+2013) anywhere: code, UI strings, comments, commit messages, PR descriptions, or Markdown. Use a hyphen (-), a colon, or a period.
- NEVER leave placeholder comments or stubs (`TODO`, `FIXME`, `implement later`, `... existing code`, `pass  # placeholder`). Ship complete, production-hardened implementations with error handling.

- No bloated abstractions or speculative generality. No dependency unless it removes more complexity than it adds.

### Law 3 - Autonomous PR and merge loop
For every task:
1. `git checkout main && git pull` then create a clean branch: `git checkout -b <type>/<short-slug>` (type = feat, fix, chore, docs, refactor).
2. Commit atomic changes with conventional commit messages.
3. `git push -u origin HEAD` and open a PR with `gh pr create --fill` (or an explicit `--title`/`--body` that lists changes, assumptions, and verification).
4. Review your own diff immediately (`gh pr diff`): security (secrets, injection, unsafe input handling, permissions), logic (edge cases, error paths), and build (run the build, linters, and tests locally).
5. Fix anything you find, push again, and repeat the review.
6. If builds and tests pass, merge it yourself: `gh pr merge --squash --delete-branch` (use `--auto` when required checks are still running), then `git checkout main && git pull`.
7. If the repo has no remote or `gh` is not authenticated, commit on a branch, merge locally into main with `git merge --squash`, and note it in the task summary.
